reasonable, in my opinion.

Email Gateway (Oct 11 2026 at 14:45):

From: Mathias Fleury <mathias.fleury12@gmail.com>

Hi Makarius,

Please do not read this timeout. It is not solving problems, it is only
adding instability to the overall system and a dependency to the CPU
power of the solver.

The problem of the timeout is that it measure the time between the
beginning of the smt tactic and the moment it is proven. Except that
with isabelle build a lot of jobs and launched and it can take a lot
of time between the beginning of the tactic and the moment it is really
executed. This timeout has lead in the past to issues in the AFP
(spurious timeout that you cannot reproduce) and in Isabelle/HOL itself
(if you run Isabelle on an underpowered machine).

For everyone who has never seen this: take your favorite theory, open
the timing panel, look at the three slowest tactics. Now rerun the file
and compare the timings. Some will be faster, some will be slower by
(from what I have seen) around one order of magnitude. A hard timeout
means that you might have to run Isabelle several times to build
dependencies, because it will depend if that tactic is slow or fast
during that run.

Mathias

From: Peter <cl-isabelle-users@lists.cam.ac.uk>

Just for my understanding: Isn't the underlying problem that the veriT
process somehow becomes detached from its controlling Isabelle session?
Ideally, all processes should be killed when the underlying sledgehammer
command is cancelled, isn't it? "Fixing" that by accepting that this
doesn't happen and simply setting a timeout looks like an ad-hoc
solution to me, with potential problems for replay stability as laid out
further in this thread.

Are the rogue veriT processes only caused by sledgehammer, or also by
proper (non-diagnostic) commands like apply? If the former is the case,
couldn't we just add the timeout when invoking veriT from sledgehammer,
but leave it without timeout when invoked as tactic?

--

Peter

On 11/10/2026 16:45, Mathias Fleury wrote:

Please do not read this timeout. It is not solving problems, it is only adding
instability to the overall system and a dependency to the CPU power of the
solver.

The problem of the timeout is that it measure the time between the beginning
of the smt tactic and the moment it is proven. Except that with isabelle build a lot of jobs and launched and it can take a lot of time between the
beginning of the tactic and the moment it is really executed. This timeout has
lead in the past to issues in the AFP (spurious timeout that you cannot
reproduce) and in Isabelle/HOL itself (if you run Isabelle on an underpowered
machine).

I do agree that timeouts are generally evil, but we have different situations
for timeouts, and different partial attempts to make them more robust.

Note that it is not the case that the timeout is on the smt tactic/proof
method. The smt_timeout is for an external process running on its own, so it
is the best possible situation. The timeout could be also scaled with Isabelle
system option timeout_scale.

Despite this best case of a bad situation, I do see smt process failures
routinely, even without the timeout: notably "z3" on x86_64-darwin or
arm64-darwin. Under heavy load with many parallel build process, it is very
unreliable. That might be a problem of this particularly old z3 version, or a
general problem on the SMT setup elsewhere.

For everyone who has never seen this: take your favorite theory, open the
timing panel, look at the three slowest tactics. Now rerun the file and
compare the timings. Some will be faster, some will be slower by (from what I
have seen) around one order of magnitude. A hard timeout means that you might
have to run Isabelle several times to build dependencies, because it will
depend if that tactic is slow or fast during that run.

The timing panel is the worst-case situation on timeouts: it essentially shows
Isabelle/ML tasks running inside a parallel LISP machine with GC happening in
between. Some years ago, I have made some attempts to distinguish timeouts
with or without GC time; there is also timeout_scale applied by default. None
of this is really reliable.

The ML timeout problem remains open and needs to be revisited eventually. (Not
now, not for this release.)

Sledgehammer timeouts can probably be improved independently, by managing the
external Isabelle bash processes via Isabelle/Scala (with the existing process
timeout), instead of anything in Isabelle/ML --- nor a soft limit on the
external program.

Timeouts in Isabelle/ML generally depend on more side-conditions than outside
of Isabelle/ML, notably Isabelle/Scala.

Since the current purpose is to manage an external process, it is better to
pass the timeout directly into Bash.timeout, which then ends up in a watchdog
thread on the JVM. At given times, that will produce a "kill" on the external
process. That is the most direct way to do it in Isabelle, everything else
will eventually come to that mechanism (if nothing else goes wrong on the way).
