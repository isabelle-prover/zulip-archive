From: Martin Desharnais-Schäfer <martin.desharnais-schaefer@posteo.de>

Hi David,

I started to have a look at this report and have the following
preliminary analysis. (Read this with a grain of salt, as I am looking
at the code generator for the first time.)

The compiler runs out of registers while constructing the tuples and
temporarily saves values on the ML stack. The garbage collector scans
that stack to find live objects. Ordinary ML integers carry a tag that
distinguishes them from pointers, but compiler-generated tuple lengths
are raw, untagged numbers. Saving those lengths on the scanned stack can
therefore make GC mistake a number for a pointer.

The register allocator has a spill-selection heuristic and a fallback
used when actual register assignment fails. The normal heuristic ranks
untagged values last; the fallback lacks the corresponding restriction.

A tentative change would make the ARM64 fallback skip RegPropUntagged
and RegPropMultiple, alongside RegPropStack. This could prevent
selection of untagged temporaries and conditional-result registers that
must not be spilled.

However, I am still puzzled by the fact the x86 does not exhibit the
same behaviour; its code does not seem to have special check for this,
but I failed to produce a SML program proving that this could still happen.

I did manage to reduce the size of the reproducing program (see further
down).

I hope that this can help you.

Regards,
Martin

Dear colleagues,

at this rather late stage of the Isabelle2026 release process, I need to
distinguish isabelle-users threads that are relevant to it from those that are
for later ("Not now, not for this release").

So I have collected the attached examples bad1.ML + bad2.ML from this thread
and made some quick tests on the following machine:

Mac14,12 -- MacMini M2 Pro, 6+4 cores
macOS 13.7.8 Ventura
arm64_32-darwin

Here are the results for recent Isabelle releases:

Isabelle2022:

- bad1.ML: OK
- bad2.ML: crash of poly
Isabelle2023, Isabelle2024, Isabelle2025, Isabelle2025-2:

- bad1.ML: crash of poly
- bad2.ML: 1. OK, 2. crash of poly
Isabelle2026-RC3:

- bad1.ML: crash of poly
- bad2.ML: 1. OK, 2. crash of poly

I have not seen a "wrong result" of bad2.ML.

On Isabelle2026-RC3, it does work for arm64-darwin and x86_64_32-darwin. (For
Isabelle2026-RC4 the x86_64 variants of Poly/ML will be included in the
regular macos_arm distribution again --- they were absent before, due to the
split of "macos" vs. "macos_arm".)

Overall it looks like the arm64_32 codegenerator was never quite right for
this rather unusual use of Poly/ML. The example appears to emulate mutable
records, but we never do that in Isabelle/ML as far as I can tell.

My current conclusion: This incident is not relevant for the Isabelle2026, and
there is plenty of time to revisit ARM64 code generation later, not in a rush.

Side-remark: It is certainly possible to break Poly/ML, Isabelle/ML,
Isabelle/Scala in many ways, by using it in so far unprecented ways. Our usual
working assumption is that applications are somewhere in the inhabitable area
defined by Isabelle Distribution + AFP, which is already quite a lot of open
space and variance.

Makarius
