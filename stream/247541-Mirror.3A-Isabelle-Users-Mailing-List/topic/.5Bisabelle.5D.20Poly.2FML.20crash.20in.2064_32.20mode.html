Hi,

I see recurring crashes in Poly/ML's 64_32 mode on ARM64.

It appears that a raw value can be spilled onto the ML stack and then interpreted as an object during GC. I leave the proper diagnosis and proper fix to the experts.

I tested the reproducer below with polyml-5.9.2-2, polyml-5.9.2-4, and polyml-5.9.2-5 shipped in Isabelle-2026-RC3. It’s an artificial example, but the problem was encountered “in the wild”.

From: Martin Desharnais-Schäfer <martin.desharnais-schaefer@posteo.de>

Hi David,

I started to have a look at this report and have the following
preliminary analysis. (Read this with a grain of salt, as I am looking
at the code generator for the first time.)

The compiler runs out of registers while constructing the tuples and
temporarily saves values on the ML stack. The garbage collector scans
that stack to find live objects. Ordinary ML integers carry a tag that
distinguishes them from pointers, but compiler-generated tuple lengths
are raw, untagged numbers. Saving those lengths on the scanned stack can
therefore make GC mistake a number for a pointer.

The register allocator has a spill-selection heuristic and a fallback
used when actual register assignment fails. The normal heuristic ranks
untagged values last; the fallback lacks the corresponding restriction.

A tentative change would make the ARM64 fallback skip RegPropUntagged
and RegPropMultiple, alongside RegPropStack. This could prevent
selection of untagged temporaries and conditional-result registers that
must not be spilled.

However, I am still puzzled by the fact the x86 does not exhibit the
same behaviour; its code does not seem to have special check for this,
but I failed to produce a SML program proving that this could still happen.

I did manage to reduce the size of the reproducing program (see further
down).

I hope that this can help you.

Regards,
Martin
